# 特征工程与实时推荐

> 在推荐系统中，"数据和特征决定了效果的上限，模型只是逼近这个上限"。本文讲解推荐系统中的特征工程实践，以及如何构建实时推荐能力。

## 🏗️ 特征体系

```
推荐系统的特征分为四大类:

┌─────────────────────────────────────────────┐
│                                              │
│  用户侧特征 (User Features)                  │
│  ├── 静态属性: 年龄、性别、城市、注册时间     │
│  ├── 统计特征: 7日点击数、平均观看时长        │
│  ├── 兴趣标签: 偏好类别、偏好作者            │
│  └── 行为序列: 最近 50 次点击的物品 ID        │
│                                              │
│  物品侧特征 (Item Features)                  │
│  ├── 静态属性: 类别、标签、作者、发布时间     │
│  ├── 内容特征: 标题 emb、封面图 emb          │
│  ├── 统计特征: 总曝光数、CTR、平均时长        │
│  └── 实时统计: 最近 1 小时的 CTR              │
│                                              │
│  交叉特征 (Cross Features)                   │
│  ├── 用户对该类别的历史 CTR                   │
│  ├── 用户对该作者的互动次数                   │
│  └── 用户 emb 与物品 emb 的余弦相似度        │
│                                              │
│  上下文特征 (Context Features)               │
│  ├── 时间: 小时、星期几、是否节假日           │
│  ├── 设备: 手机型号、操作系统、屏幕尺寸       │
│  └── 场景: 首页推荐 / 详情页推荐 / 搜索结果  │
│                                              │
└─────────────────────────────────────────────┘
```

## 📊 特征处理方法

### 数值特征

```
原始值: 用户年龄 = 28

处理方法:
  1. 归一化: (28 - mean) / std
  2. 分桶: [0-18, 18-25, 25-35, 35-50, 50+] → 桶 3
  3. 对数变换: log(1 + x)  ← 适合长尾分布 (如播放量)

推荐系统中常用分桶:
  将连续值离散化 → 转为 Embedding → 模型更容易学习非线性关系
  
  例如价格分桶:
  [0-10, 10-50, 50-100, 100-500, 500+]
  每个桶有自己的 Embedding 向量
```

### 类别特征

```
原始值: 城市 = "北京"

处理方法:
  1. One-Hot: [1, 0, 0, ..., 0]  ← 城市太多时维度爆炸
  2. Embedding: 城市ID → Embedding 查表 → 32维向量  ← 推荐做法
  3. 哈希: hash("北京") % 10000 → 桶ID → Embedding

多值类别 (用户兴趣标签 = ["科技", "美食", "旅游"]):
  方法 1: 多个 Embedding 求平均
  方法 2: 多个 Embedding 加权求和 (权重可学习)
  方法 3: 用注意力机制聚合
```

### 序列特征

```
用户最近点击序列: [item_23, item_456, item_78, item_901, item_12]

处理方法:
  1. Pooling: 所有 item Embedding 求平均
  2. 加权 Pooling: 越近的行为权重越大
  3. DIN: 用注意力机制，根据候选物品加权
  4. Transformer: 用 Self-Attention 建模序列关系

  序列长度选择:
    太短 (10): 信息不足
    太长 (1000): 计算成本高，噪声多
    常用: 50-200
```

## ⏱️ 特征的时效性

```
┌──────────────────────────────────────────────────┐
│  时效性        更新频率      示例                  │
├──────────────────────────────────────────────────┤
│  离线特征      天级         用户画像、物品统计     │
│  近实时特征    分钟级       最近 1 小时 CTR        │
│  实时特征      秒级         当前 session 行为序列  │
└──────────────────────────────────────────────────┘

越实时的特征，对推荐效果的提升越大
但工程实现的复杂度也越高
```

### 实时特征的价值

```
场景: 用户刚搜索了 "跑步鞋"

  没有实时特征:
    推荐系统不知道用户刚搜索了跑步鞋
    → 推荐的还是之前的兴趣 (比如手机)

  有实时特征:
    实时捕捉到搜索行为
    → 立即推荐跑步鞋相关商品
    → 点击率大幅提升
```

## 🔄 Feature Store（特征平台）

```
┌─────────────────────────────────────────────────┐
│                Feature Store                     │
│                                                  │
│  离线存储 (Batch)          在线存储 (Online)      │
│  ┌──────────────┐         ┌──────────────┐      │
│  │ Hive / HDFS  │ ──ETL─→ │ Redis / HBase│      │
│  │ 天级更新     │         │ 毫秒级读取   │      │
│  └──────────────┘         └──────────────┘      │
│                                  ↑               │
│  流式计算 (Stream)               │               │
│  ┌──────────────┐               │               │
│  │ Flink / Kafka│ ──实时写入──→ │               │
│  │ 秒级更新     │                               │
│  └──────────────┘                               │
│                                                  │
│  推荐服务请求特征:                               │
│    1. 用户 ID → 查 Redis → 用户特征              │
│    2. 物品 ID → 查 Redis → 物品特征              │
│    3. 拼接特征 → 送入模型                        │
│    总耗时: < 20ms                                │
└─────────────────────────────────────────────────┘
```

## 🚀 实时推荐系统

### 实时推荐的三个层次

```
Level 1: 近实时特征更新 (分钟级)
  用户行为 → Kafka → Flink 聚合 → 更新 Redis 中的统计特征
  例如: 每 5 分钟更新用户的兴趣标签

Level 2: 实时行为序列 (秒级)
  用户每次点击 → 实时追加到行为序列
  下次请求推荐时，模型能看到最新的行为
  例如: 用户刚点了一双跑步鞋 → 下一屏推荐运动装备

Level 3: 实时模型更新 (小时级)
  用新产生的数据增量更新模型参数
  例如: Online Learning，每小时用新数据微调模型
```

### Online Learning（在线学习）

```
传统方式:
  收集一天的数据 → 离线训练模型 → 第二天上线
  问题: 模型永远滞后一天

Online Learning:
  实时收集数据 → 增量更新模型 → 立即生效

  ┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐
  │ 用户  │ →  │ 行为  │ →  │ 训练  │ →  │ 模型  │
  │ 行为  │    │ 日志  │    │ 样本  │    │ 更新  │
  └──────┘    └──────┘    └──────┘    └──────┘
                                          ↓
                                     推荐服务使用新模型

  更新频率: 通常每 15 分钟 ~ 1 小时
  
  挑战:
    - 样本延迟: 用户点击后可能很久才产生转化
    - 数据质量: 实时数据可能有噪声
    - 模型稳定性: 频繁更新可能导致模型震荡
```

### 实时推荐的工程挑战

```
┌─────────────────────────────────────────────┐
│  挑战              解决方案                   │
├─────────────────────────────────────────────┤
│  特征一致性        Feature Store 统一管理    │
│  (训练和推理用     离线和在线使用相同的       │
│   同样的特征)      特征计算逻辑              │
│                                              │
│  样本拼接          用 Kafka 实时拼接          │
│  (把特征和标签     曝光时记录特征快照         │
│   对齐)            点击/转化时回填标签        │
│                                              │
│  数据倾斜          负采样 + 加权              │
│  (正样本远少于     控制正负样本比例           │
│   负样本)                                    │
│                                              │
│  延迟要求          特征预计算 + 缓存          │
│  (100ms 内完成)    模型量化 + 批量推理        │
└─────────────────────────────────────────────┘
```

## 🔑 特征工程的实践经验

### 1. 特征重要性分析

```
方法:
  - 模型自带的特征重要性 (GBDT)
  - 逐个去掉特征看 AUC 变化
  - SHAP 值分析

通常发现:
  用户行为序列特征 > 交叉特征 > 统计特征 > 静态属性
  
  最重要的特征往往是:
  1. 用户最近的行为序列
  2. 物品的实时 CTR
  3. 用户对该类别的历史偏好
```

### 2. 特征交叉的艺术

```
有效的交叉特征:
  ✅ 用户性别 × 物品类别 (女性偏好化妆品)
  ✅ 用户年龄段 × 物品价格段 (年轻人偏好平价)
  ✅ 时间段 × 物品类别 (深夜偏好零食外卖)
  ✅ 用户活跃度 × 物品热度 (活跃用户更愿意探索冷门)

无效的交叉特征:
  ❌ 用户 ID × 物品 ID (太稀疏，没有泛化能力)
  ❌ 不相关的特征交叉 (用户身高 × 物品颜色)
```

### 3. 处理数据偏差

```
位置偏差 (Position Bias):
  排在第一位的物品天然获得更多点击
  → 训练时加入位置特征，推理时去掉

曝光偏差 (Exposure Bias):
  模型只能从已曝光的物品中学习
  → 随机探索 (ε-greedy)、IPW 加权

选择偏差 (Selection Bias):
  用户只对感兴趣的物品评分
  → 使用隐式反馈、因果推断方法
```

## 小结

- 特征工程是推荐系统效果的关键，好的特征比复杂的模型更重要
- 实时特征能显著提升推荐效果，但工程复杂度高
- Feature Store 是管理特征的核心基础设施
- Online Learning 让模型能快速适应用户兴趣变化
- 数据偏差处理是容易被忽视但很重要的环节
