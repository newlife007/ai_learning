# 推荐系统的工程架构：召回、排序、重排

> 算法只是推荐系统的一部分。要在毫秒级延迟内从亿级候选中选出最合适的内容，需要精心设计的工程架构。本文详解工业级推荐系统的经典漏斗架构。

## 🏗️ 为什么需要漏斗架构

```
直接用最精确的模型对所有物品打分？

  物品数量: 10 亿
  精排模型推理: 1ms / 个
  总耗时: 10 亿 × 1ms = 100 万秒 ≈ 11.6 天

  用户能等 11 天吗？显然不行。

解决方案: 漏斗架构 — 逐层过滤，越往后模型越精确但候选越少

  10 亿 →[召回]→ 1 万 →[粗排]→ 500 →[精排]→ 50 →[重排]→ 20
  
  总耗时: ~100ms  ✅
```

## 📐 四层漏斗详解

```
┌─────────────────────────────────────────────────┐
│                                                  │
│  全量物品池                          10 亿+      │
│  ████████████████████████████████████████████    │
│                                                  │
│  ┌──────────────────────────────────────────┐   │
│  │ 召回层 (Recall)              ~10ms       │   │
│  │ 多路召回，快速筛选            → 1 万      │   │
│  └──────────────────────────────────────────┘   │
│                                                  │
│     ┌──────────────────────────────────┐        │
│     │ 粗排层 (Pre-Ranking)    ~10ms    │        │
│     │ 轻量模型初筛             → 500    │        │
│     └──────────────────────────────────┘        │
│                                                  │
│        ┌──────────────────────────┐             │
│        │ 精排层 (Ranking)  ~30ms  │             │

└─────────────────────────────────────────────────┘
```

## 1️⃣ 召回层（Recall）

### 目标

从全量物品中快速找出用户可能感兴趣的候选集。要求：**快、全（不遗漏好的物品）**。

### 多路召回

```
用户请求到达
    │
    ├──→ 协同过滤召回 (ItemCF)     → 200 个
    ├──→ 向量召回 (双塔模型)       → 300 个
    ├──→ 热门召回                  → 100 个
    ├──→ 标签/类别召回             → 200 个
    ├──→ 最近交互的相似物品召回     → 100 个
    └──→ 地理位置召回 (本地内容)   → 100 个
    │
    ▼
  合并去重 → ~1000 个候选
```

每路召回独立运行，并行执行，最后合并去重。

### 向量召回（最重要的召回方式）

```
离线阶段:
  用户 → 用户塔 (User Tower) → 用户向量 (128维)
  物品 → 物品塔 (Item Tower) → 物品向量 (128维)
  所有物品向量存入向量索引 (FAISS / Milvus)

在线阶段:
  1. 计算当前用户的向量
  2. 在向量索引中做 ANN 搜索
  3. 返回最相似的 top-K 物品

  耗时: ~5ms (即使物品有 1 亿个)
```

### 召回的关键指标

```
召回率 (Recall@K):
  在返回的 K 个候选中，包含了多少用户真正会交互的物品

  例如: 用户最终会点击 10 个物品
        召回的 1000 个候选中包含了其中 8 个
        Recall@1000 = 8/10 = 80%

  召回率越高越好 — 好物品不能在这一步被漏掉
```

## 2️⃣ 粗排层（Pre-Ranking）

### 目标

用轻量模型快速过滤，将候选从 ~1000 缩减到 ~500。

```
为什么需要粗排？

  精排模型很复杂 (几百个特征，多层网络)
  对 1000 个候选精排: ~30ms × 1000 = 30s  ❌
  对 500 个候选精排:  ~30ms × 500 = 15s   还是太慢

  实际上精排是批量推理，500 个候选约 30ms
  但如果候选太多，精排的延迟和计算成本都会增加
```

### 粗排模型

```
常用方案:
  - 简化版双塔模型 (特征少、网络浅)
  - 知识蒸馏: 用精排模型的输出训练一个小模型
  - 简单的 LR / 浅层 NN

要求: 推理速度快 (单个候选 <0.1ms)
```

## 3️⃣ 精排层（Ranking）

### 目标

用最精确的模型对候选物品打分排序。这是推荐系统中模型最复杂、效果最关键的环节。

### 精排模型的输入

```
┌─────────────────────────────────────────────┐
│ 用户特征:                                    │
│   基础: 年龄、性别、城市、注册天数            │
│   行为: 最近点击的 50 个物品 ID               │
│   统计: 过去 7 天点击率、平均观看时长          │
│   实时: 当前 session 的行为序列               │
│                                              │
│ 物品特征:                                    │
│   基础: 类别、标签、作者、发布时间            │
│   统计: 总点击数、点击率、平均观看时长         │
│   内容: 标题 embedding、封面图 embedding      │
│                                              │
│ 交叉特征:                                    │
│   用户对该类别的历史点击率                    │
│   用户对该作者的历史互动次数                  │
│   用户与物品的 embedding 相似度               │
│                                              │
│ 上下文特征:                                  │
│   时间 (小时、星期几)、设备、网络环境         │
└─────────────────────────────────────────────┘

  特征总数: 几百到几千个
```

### 精排模型的输出

```
通常是多目标预测:

  P(点击)    = 0.15    (点击率预估)
  P(点赞)    = 0.03    (点赞率预估)
  P(收藏)    = 0.02    (收藏率预估)
  P(分享)    = 0.01    (分享率预估)
  E(观看时长) = 45s     (预估观看时长)

最终排序分 = 加权融合:
  score = w1 × P(点击) + w2 × P(点赞) + w3 × P(收藏) 
        + w4 × P(分享) + w5 × E(时长)

  权重由业务目标决定:
    追求用户活跃: 提高 P(点击) 的权重
    追求用户留存: 提高 E(时长) 的权重
    追求社交传播: 提高 P(分享) 的权重
```

### 主流精排模型

```
模型演进:

  LR (逻辑回归)
    ↓ 无法自动学习特征交叉
  GBDT + LR (Facebook, 2014)
    ↓ 特征工程繁重
  FM / FFM (因子分解机)
    ↓ 只能二阶交叉
  Wide & Deep (Google, 2016)
    ↓
  DeepFM (2017)
    ↓
  DIN (阿里, 2018)  ← 引入注意力机制
    ↓
  DIEN (阿里, 2019) ← 建模兴趣演化
    ↓
  多任务模型 (MMOE, PLE)
    ↓
  Transformer-based (SIM, DSIN)
```

后续文章会详细讲解这些模型。

## 4️⃣ 重排层（Re-Ranking）

### 目标

在精排结果基础上，加入业务规则和策略，生成最终展示列表。

### 常见重排策略

```
┌─────────────────────────────────────────────┐
│ 策略              说明                       │
├─────────────────────────────────────────────┤
│ 去重              同一作者/来源不连续出现     │
│ 多样性            不同类别交替展示            │
│ 新鲜度            给新内容一定的曝光机会      │
│ 广告插入          在合适位置插入广告          │
│ 运营干预          置顶/加权特定内容           │
│ 频控              同一物品不重复推荐          │
│ 打散              避免同类内容扎堆            │
│ 合规过滤          过滤违规/敏感内容           │
└─────────────────────────────────────────────┘
```

### 多样性：MMR 算法

```
MMR (Maximal Marginal Relevance):

  在选择下一个推荐物品时，同时考虑:
    1. 与用户的相关性 (越高越好)
    2. 与已选物品的差异性 (越大越好)

  score = λ × relevance(item, user) 
        - (1-λ) × max_similarity(item, selected_items)

  λ 控制相关性和多样性的平衡
```

### Listwise 重排

```
传统精排: 对每个物品独立打分 (Pointwise)
Listwise 重排: 考虑物品之间的关系，优化整个列表

  例如: 用户看了 3 个美食视频后，第 4 个推旅游视频
        → 提升用户体验，减少审美疲劳

  方法: 用 Transformer 对候选列表建模
        输入: 精排后的候选序列
        输出: 重新排序后的列表
```

## 小结

工业级推荐系统的漏斗架构是一个精心设计的工程方案：
- **召回**：多路并行，快速筛选，保证不遗漏好物品
- **粗排**：轻量模型，快速过滤，降低精排压力
- **精排**：复杂模型，精确打分，决定推荐质量
- **重排**：业务策略，多样性控制，最终用户体验

每一层都在速度和精度之间做权衡，共同在 100ms 内完成从亿级候选到最终展示的全过程。
