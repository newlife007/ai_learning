# 博客四：广告平台架构设计 — 从投放到展示的全链路

> 系列文章第 4 篇 / 共 7 篇

## 引言

前三篇我们了解了广告平台的历史、解决的问题和核心概念。这篇进入技术层面——一个广告平台的系统架构长什么样？从广告主创建一条广告，到用户在手机上看到它，中间经过了哪些系统模块？

我们以一个典型的信息流广告平台（类似巨量引擎/腾讯广告）为参考，拆解其架构设计。

## 1. 全局架构概览

一个完整的广告平台可以分为两大部分：**投放侧**（广告主操作）和**展示侧**（用户看到广告），中间由**广告引擎**连接。

```
┌─────────────────────────────────────────────────────────────────┐
│                        广告平台全局架构                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌──────────────┐   ┌──────────────┐   ┌──────────────────┐    │
│  │  投放管理系统  │   │  广告引擎     │   │  数据与算法平台   │    │
│  │  (广告主侧)   │   │  (核心链路)   │   │  (支撑系统)      │    │
│  ├──────────────┤   ├──────────────┤   ├──────────────────┤    │
│  │ 账户管理     │   │ 广告检索     │   │ 用户画像(DMP)    │    │
│  │ 广告创建     │   │ 定向匹配     │   │ 特征工程         │    │
│  │ 素材管理     │   │ 竞价排序     │   │ 模型训练         │    │
│  │ 审核系统     │   │ 预算控制     │   │ 实时数据流       │    │

│  │ 财务结算     │   │ 创意优选     │   │ A/B 实验平台     │    │

│                            │                                    │
│                     ┌──────┴──────┐                             │

│                     │  (媒体接入)  │                             │

│                            │                                    │
```

## 2. 投放管理系统（广告主侧）

这是广告主直接操作的系统，通常是一个 Web 后台 + API。

### 2.1 核心模块

```
投放管理系统
├── 账户中心
│   ├── 注册/认证（企业资质审核）
│   ├── 充值/余额管理
│   └── 权限管理（多角色：管理员/优化师/财务）
│
├── 广告管理
│   ├── 创建广告（Campaign → Ad Group → Creative）
│   ├── 定向设置
│   ├── 出价设置（CPC/CPM/oCPX）
│   └── 预算与排期
│
├── 素材中心
│   ├── 图片/视频上传与管理
│   ├── 落地页管理
│   └── 动态创意（多素材自动组合）
│
├── 审核系统
│   ├── 机器审核（图片 OCR、视频帧检测、文本敏感词）
│   ├── 人工审核（机器不确定的交给人工）
│   └── 行业资质审核（医疗、金融等特殊行业）
│
├── 数据报表
│   ├── 实时数据（展示/点击/转化/花费）
│   ├── 多维分析（按时间/地域/人群/创意拆分）
│   └── 归因报告
│
└── 财务结算
    ├── 预付费模式（先充值后消耗）
    ├── 账单与发票
    └── 退款处理
```

### 2.2 技术要点

投放管理系统本质上是一个**管理后台 + CRUD 系统**，但有几个特殊点：

```
1. 广告数据的生效链路
   广告主修改出价 → 写入数据库 → 同步到广告引擎的索引
   这个同步延迟通常要求在 分钟级别 内完成

2. 审核系统的吞吐量
   大平台每天新增数百万条创意，审核系统需要：
   - 机器审核：秒级完成，准确率 > 95%
   - 人工审核：分钟级完成，处理机器不确定的 case

3. 数据报表的实时性
   广告主期望看到 准实时 的数据（延迟 < 5分钟）
   需要实时数据流（Kafka/Flink）+ 预聚合
```

## 3. 广告引擎（核心链路）

这是广告平台最核心、技术含量最高的部分。每一次广告请求（用户打开 App 的一次刷新），都要经过这条链路。

### 3.1 一次广告请求的完整流程

```
用户打开抖音，下滑刷新
    │
    ▼
[1] 广告请求（Ad Request）
    App 向广告引擎发送请求
    携带信息：用户ID、设备信息、地理位置、当前内容上下文
    │
    ▼
[2] 用户识别与画像获取
    根据设备ID/用户ID，从 DMP 获取用户画像
    年龄、性别、兴趣标签、近期行为等
    │
    ▼
[3] 广告召回（Recall / Retrieval）
    从全量广告库中，快速筛选出可能相关的候选广告
    通常从 百万级 广告中筛选出 数千条 候选
    │
    ▼
[4] 定向过滤（Targeting Filter）
    根据广告主设定的定向条件，过滤不匹配的广告
    数千条 → 数百条
    │
    ▼
[5] 预算与频次过滤
    过滤掉预算已耗尽的广告
    过滤掉该用户已看过太多次的广告
    数百条 → 数十到数百条
    │
    ▼
[6] CTR/CVR 预估（Ranking）
    用机器学习模型预估每条广告的点击率和转化率
    这是最消耗算力的环节
    │
    ▼
[7] 竞价排序（Auction）
    排序分 = 出价 × pCTR × pCVR × 质量度
    选出排序分最高的广告
    │
    ▼
[8] 定价（Pricing）
    按 GSP（广义第二价格）计算实际扣费
    │
    ▼
[9] 广告返回与展示
    返回广告素材（图片/视频 URL、文案、落地页）
    App 渲染展示
    │
    ▼
[10] 事件上报
     展示上报 → 点击上报 → 转化上报
     用于计费、数据报表、模型训练
```

### 3.2 性能要求

整个流程必须在极短时间内完成：

```
总延迟预算：~100ms（从收到请求到返回广告）

各环节延迟分配（参考）：
  用户画像获取：  ~10ms（Redis/内存缓存）
  广告召回：      ~15ms（倒排索引）
  定向过滤：      ~5ms
  预算频次过滤：  ~5ms
  CTR/CVR 预估：  ~30ms（模型推理）
  竞价排序：      ~5ms
  其他开销：      ~30ms（网络、序列化等）
```

QPS（每秒请求数）要求：

```
以抖音为例（估算）：
  日活用户：~7亿
  人均刷新次数：~100次/天
  广告请求占比：~15%（不是每次刷新都有广告位）
  
  峰值 QPS ≈ 7亿 × 100 × 15% / 86400 × 3（峰值系数）
           ≈ 约 36万 QPS

这意味着广告引擎需要：
  - 大规模分布式部署（数千台服务器）
  - 极致的性能优化
  - 高可用设计（99.99%+）
```

### 3.3 广告召回的实现

召回是从海量广告中快速找到候选集的过程，类似搜索引擎的检索。

```
召回策略（多路召回）：

1. 倒排索引召回
   建立 "定向条件 → 广告列表" 的倒排索引
   例：兴趣标签"运动" → [广告A, 广告B, 广告C, ...]
   
2. 向量召回
   将用户和广告都编码为向量
   用 ANN（近似最近邻）检索最相似的广告
   工具：Faiss、Milvus、HNSW

3. 热门广告召回
   高 CTR、高预算的广告直接进入候选集

4. 重定向召回
   用户之前交互过的广告主的其他广告

多路召回结果合并去重 → 进入后续排序环节
```

### 3.4 排序模型

排序是广告引擎中最核心的算法环节，通常分为粗排和精排：

```
召回（数千条）
    ↓
粗排（Rough Ranking）
    简单模型快速打分，筛选到 数百条
    模型：LR、轻量 DNN
    ↓
精排（Fine Ranking）
    复杂模型精确打分
    模型：Deep & Cross Network、DeepFM、DIN 等
    输入特征：用户特征 + 广告特征 + 上下文特征 + 交叉特征
    输出：pCTR（预估点击率）、pCVR（预估转化率）
    ↓
重排（Re-ranking）
    考虑多样性、频次控制、广告主间的公平性等
    最终选出要展示的广告
```

### 4.2 用户画像系统（DMP）

```
数据采集
  ├── 行为日志（浏览、搜索、点击、购买）
  ├── 设备信息（机型、OS、运营商）
  ├── 位置信息（GPS、IP）
  └── 第三方数据（合规前提下）
      ↓
特征加工
  ├── 实时特征：最近 30 分钟的行为（Flink 计算）
  ├── 近线特征：最近 7 天的行为统计（小时级更新）
  └── 离线特征：长期兴趣标签、人口属性（天级更新）
      ↓
存储与服务
  ├── Redis：高频访问的热数据（实时特征）
  ├── HBase/Cassandra：全量用户画像
  └── 特征服务：统一的特征获取 API，供广告引擎调用
```

### 4.3 模型训练平台

```
训练数据
  ├── 正样本：用户点击/转化的广告
  ├── 负样本：用户看到但没点击的广告
  └── 特征：用户特征 + 广告特征 + 上下文特征
      ↓
模型训练
  ├── 离线训练：每天用前一天的数据训练新模型
  ├── 增量训练：每小时用最新数据微调模型
  └── 在线学习：实时更新模型参数（部分场景）
      ↓
模型部署
  ├── 模型验证：离线 AUC、在线 A/B 测试
  ├── 模型上线：推送到推理服务集群
  └── 模型监控：实时监控预估值分布、CTR 偏差
```

## 5. 媒体接入层（SDK / API）

媒体（App/网站）通过 SDK 或 API 接入广告平台。

### 5.1 SDK 接入方式

```
App 集成广告 SDK 的流程：

1. 注册媒体账号，创建广告位（Ad Slot）
2. 下载 SDK，集成到 App 中
3. 在代码中初始化 SDK，配置广告位 ID
4. SDK 自动处理：
   - 广告请求
   - 广告渲染
   - 展示/点击上报
   - 缓存与预加载

SDK 提供的广告类型：
  - 信息流广告（Feed Ad）
  - 开屏广告（Splash Ad）
  - Banner 广告
  - 插屏广告（Interstitial Ad）
  - 激励视频（Rewarded Video）
```

### 5.2 Server-to-Server API 接入

```
适用于：有自己广告系统的大型媒体

流程：
  媒体服务器 → 广告平台 API（Ad Request）→ 返回广告数据
  媒体自己渲染广告 → 上报展示/点击事件

优势：
  - 媒体对广告展示有完全控制权
  - 可以混合多个广告源（Header Bidding）
  
劣势：
  - 接入成本高
  - 需要自己处理渲染和上报
```

## 6. 关键子系统详解

### 6.1 预算控制系统（Pacing）

预算控制要解决的问题：广告主设了 1000 元日预算，不能上午就花完了。

```
预算控制策略：

1. 匀速消耗（Smooth Pacing）
   将日预算均匀分配到每个小时
   1000元/天 → 约 42元/小时
   每小时消耗接近目标时，降低竞价参与率

2. 加速消耗（ASAP）
   尽快花完预算，适合限时促销
   
3. 智能调速
   根据流量波动动态调整
   高峰期多花，低谷期少花
   目标：在预算内获得最多转化

技术实现：
  - 分布式计数器（Redis）实时追踪消耗
  - 每个广告引擎节点定期同步预算状态
  - 预算快耗尽时，逐步降低参与竞价的概率
```

### 6.2 频次控制系统

```
目的：避免同一用户反复看到同一广告

控制维度：
  - 同一广告：每用户每天最多展示 3 次
  - 同一广告主：每用户每天最多展示 10 次
  - 同一行业：每用户每小时最多展示 N 次

技术实现：
  - 用户级别的展示计数器
  - 存储：Redis（热数据）+ 持久化存储
  - 在广告过滤阶段检查频次
```

### 6.3 实时计费系统

```
计费流程：

1. 广告展示 → App SDK 上报展示事件
2. 展示事件到达计费服务
3. 计费服务：
   a. 反作弊检查（是否是虚假展示）
   b. 计算扣费金额（GSP 定价）
   c. 扣减广告主余额
   d. 写入计费日志
4. 计费日志用于：
   - 广告主的实时花费报表
   - 媒体的收入结算
   - 财务对账

关键要求：
  - 不能多扣（损害广告主利益）
  - 不能少扣（损害平台收入）
  - 高并发下的一致性（分布式事务）
  - 幂等性（同一事件不能重复计费）
```

## 9. 架构设计的核心挑战

| 挑战 | 说明 | 应对方案 |
|------|------|---------|
| 超低延迟 | 100ms 内完成全链路 | C++/Go 实现核心链路，内存计算，预加载 |
| 超高并发 | 数十万 QPS | 分布式部署，无状态设计，本地缓存 |
| 数据一致性 | 预算不能超花，计费不能出错 | 分布式计数器，最终一致性，对账机制 |
| 模型实时性 | 用户兴趣变化快 | 实时特征 + 在线学习 + 增量更新 |
| 高可用 | 广告是核心收入，不能挂 | 多机房部署，降级策略，熔断机制 |
| 可扩展性 | 广告主和流量持续增长 | 水平扩展，微服务架构 |

---

## 小结

广告平台的架构可以概括为三大部分：

1. **投放管理系统**：广告主的操作界面，本质是管理后台，但有审核、实时报表等特殊需求
2. **广告引擎**：核心链路，从召回→过滤→排序→竞价→展示，100ms 内完成，数十万 QPS
3. **数据与算法平台**：用户画像、特征工程、模型训练，是广告引擎的"大脑"

其中广告引擎是技术难度最高的部分，需要在极短时间内完成复杂的决策过程。下一篇我们深入广告引擎中的关键技术：竞价算法、推荐模型、反作弊系统。
