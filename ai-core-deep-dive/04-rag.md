# RAG：检索增强生成

> LLM 的知识是"冻结"在训练数据中的，无法获取最新信息，也容易产生幻觉。RAG（Retrieval-Augmented Generation）通过在生成前检索相关文档，让模型基于真实数据回答问题。

## 为什么需要 RAG

LLM 的固有局限：

| 问题 | 说明 |
|------|------|
| 知识截止 | 训练数据有截止日期，无法回答最新问题 |
| 幻觉 | 自信地编造不存在的事实 |
| 领域知识不足 | 对企业内部文档、专业领域知识了解有限 |
| 不可溯源 | 无法指出答案来自哪个文档 |

RAG 的解决思路：**不要让模型凭记忆回答，而是先帮它找到相关资料，再让它基于资料回答。**

## 基本架构

```
用户问题
  ↓
[1. 检索] 从知识库中找到相关文档片段
  ↓
[2. 增强] 将文档片段拼接到 prompt 中
  ↓
[3. 生成] LLM 基于 prompt + 文档生成回答
```

一个典型的 RAG prompt：

```
请根据以下参考资料回答用户问题。如果资料中没有相关信息，请说明。

参考资料：
[1] {检索到的文档片段 1}
[2] {检索到的文档片段 2}
[3] {检索到的文档片段 3}

用户问题：{question}
```

## 核心组件详解

### 1. 文档处理与分块（Chunking）

将原始文档切分成适合检索的片段：

```
原始文档 → 分块 → 向量化 → 存入向量数据库
```

常见分块策略：

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| 固定大小 | 按字符/token 数切分 | 通用 |
| 按段落/章节 | 按文档结构切分 | 结构化文档 |
| 语义分块 | 按语义相似度切分 | 需要高质量检索 |
| 递归分块 | 先按大结构，再按小结构 | LangChain 默认 |

分块大小的权衡：
- **太小**（<100 tokens）：缺乏上下文，检索到的片段信息不完整
- **太大**（>1000 tokens）：包含太多无关信息，稀释关键内容
- **推荐**：256-512 tokens，带 50-100 tokens 重叠

### 2. Embedding 与向量化

将文本转换为高维向量，使语义相似的文本在向量空间中距离更近：

```
"如何训练大模型" → [0.12, -0.34, 0.56, ...] (768维或1536维)
"LLM 的训练方法" → [0.11, -0.33, 0.55, ...] (语义相近，向量相近)
```

主流 Embedding 模型：

| 模型 | 维度 | 特点 |
|------|------|------|
| OpenAI text-embedding-3-small | 1536 | 商用首选 |
| BGE-large-zh | 1024 | 中文最佳开源 |
| E5-mistral-7b | 4096 | 大模型级别 embedding |
| GTE-Qwen2 | 1536 | 多语言，效果好 |

### 3. 向量检索

用户查询也被向量化，然后在向量数据库中找到最相似的文档片段：

```
相似度计算方法：
  - 余弦相似度: cos(q, d) = q·d / (|q|·|d|)  ← 最常用
  - 内积: q·d
  - 欧氏距离: ||q - d||
```

主流向量数据库：

| 数据库 | 类型 | 特点 |
|--------|------|------|
| Pinecone | 云服务 | 全托管，开箱即用 |
| Milvus | 开源 | 功能全面，支持混合检索 |
| Chroma | 开源 | 轻量级，适合原型开发 |
| pgvector | PostgreSQL 扩展 | 已有 PG 基础设施时首选 |
| FAISS | 库 | Meta 开源，纯向量搜索 |

### 4. 混合检索（Hybrid Search）

纯向量检索有时会遗漏关键词精确匹配的结果。混合检索结合两种方式：

```
混合检索 = 向量检索（语义匹配）+ 关键词检索（BM25 精确匹配）

最终分数 = α × 向量分数 + (1-α) × BM25 分数
```

例如用户搜索 "Python 3.12 新特性"：
- 向量检索可能返回 "Python 最新版本的改进"（语义相关）
- BM25 会精确匹配 "3.12" 这个关键词

两者结合效果最好。

## 高级 RAG 技术

### Query 改写

用户的原始查询可能不适合直接检索：

```
原始查询: "为什么我的代码跑不了"
改写后: "Python 常见运行时错误及解决方法"
```

常见策略：
- **HyDE**：让 LLM 先生成一个假设性回答，用回答去检索
- **多查询**：将一个问题拆成多个子查询，分别检索后合并
- **Step-back**：将具体问题抽象化，检索更通用的知识

### Reranking（重排序）

检索返回的 top-K 结果中，排序可能不够精确。用 Cross-Encoder 重排序：

```
向量检索 top-20 → Reranker 精排 → 取 top-5 送入 LLM
```

Reranker 比 Embedding 模型更精确（因为它同时看到 query 和 document），但计算成本更高，所以只用于重排少量候选。

常用 Reranker：Cohere Rerank、BGE-reranker、Jina Reranker。

### 自适应检索

不是所有问题都需要检索。让模型自己判断：

```
"1+1等于几" → 不需要检索，直接回答
"公司最新的报销政策是什么" → 需要检索
```

实现方式：
- 基于规则（关键词触发）
- 让 LLM 判断是否需要检索
- Self-RAG：模型生成过程中动态决定是否检索

### 多轮对话 RAG

在多轮对话中，需要将对话历史纳入检索：

```
用户: "介绍一下 LLaMA"
助手: "LLaMA 是 Meta 开源的大语言模型..."
用户: "它的最新版本有什么改进？"
  ↓
检索查询应该是: "LLaMA 最新版本改进" (而非 "它的最新版本")
```

需要做对话历史的 query 重写，将代词解析为具体实体。

## RAG 评估

| 指标 | 衡量什么 |
|------|---------|
| 检索召回率 | 相关文档是否被检索到 |
| 检索精确率 | 检索到的文档是否相关 |
| 答案忠实度 | 回答是否基于检索到的文档 |
| 答案相关性 | 回答是否回答了用户问题 |

常用评估框架：RAGAS、TruLens。

## RAG vs 长上下文 vs 微调

| 方案 | 适用场景 | 优势 | 劣势 |
|------|---------|------|------|
| RAG | 知识库问答 | 可溯源、实时更新 | 检索质量是瓶颈 |
| 长上下文 | 文档分析 | 简单直接 | 成本高、有长度限制 |
| 微调 | 风格/格式调整 | 无需运行时检索 | 知识更新需重新训练 |

实际中三者经常组合使用。

## 实践建议

1. **先做好分块**：分块质量决定了 RAG 的上限
2. **混合检索 > 纯向量检索**：几乎总是如此
3. **加 Reranker**：成本不高但效果提升明显
4. **评估驱动**：建立评估数据集，量化每次改进的效果
5. **处理好 "检索不到" 的情况**：让模型诚实说"我不知道"

## 小结

RAG 是当前将 LLM 落地到实际业务中最重要的技术之一。它解决了 LLM 知识过时和幻觉的核心痛点，同时提供了可溯源的回答。虽然概念简单，但要做好 RAG 需要在分块、检索、重排序、prompt 工程等每个环节精心优化。
