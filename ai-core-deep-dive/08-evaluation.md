# 模型评估与基准测试

> "如果你无法衡量它，你就无法改进它。" 模型评估是 AI 开发中最容易被忽视但最重要的环节。本文梳理主流评估方法、基准测试和实践中的评估策略。

## 为什么评估很难

LLM 的评估比传统 ML 模型困难得多：

- **开放式输出**：同一个问题可以有多种正确回答
- **多维度能力**：推理、编程、创意、安全性……无法用单一指标衡量
- **评估者偏见**：人类评估主观性强，不同评估者标准不同
- **数据污染**：模型可能在训练时见过测试数据

## 评估方法分类

```
自动评估
  ├─ 基于参考答案: BLEU, ROUGE, Exact Match
  ├─ 基于模型: LLM-as-Judge, BERTScore
  └─ 基于任务: 准确率, F1, Pass@k

人工评估
  ├─ 绝对评分: 对单个回答打分 (1-5)
  ├─ 相对评分: 比较两个回答哪个更好 (A/B Test)
  └─ 众包评估: Chatbot Arena (ELO 排名)
```

## 主流基准测试

### 综合能力

| 基准 | 评估内容 | 形式 |
|------|---------|------|
| MMLU | 57 个学科的知识 | 多选题 |
| MMLU-Pro | MMLU 升级版，更难 | 10 选 1 |
| ARC | 科学推理 | 多选题 |
| HellaSwag | 常识推理 | 句子补全 |
| WinoGrande | 指代消解 | 二选一 |
| TruthfulQA | 真实性（抗幻觉） | 多选/生成 |

**MMLU** 是最广泛使用的综合基准，涵盖从高中到研究生水平的 57 个学科。但它也有局限——多选题格式无法评估生成质量。

### 推理能力

| 基准 | 评估内容 | 说明 |
|------|---------|------|
| GSM8K | 小学数学应用题 | 8.5K 题，CoT 推理 |
| MATH | 竞赛级数学 | 难度远高于 GSM8K |
| BBH | 23 个困难推理任务 | BIG-Bench 子集 |
| ARC-Challenge | 困难科学推理 | ARC 的难题子集 |

### 编程能力

| 基准 | 评估内容 | 指标 |
|------|---------|------|
| HumanEval | 164 个 Python 编程题 | Pass@1, Pass@10 |
| MBPP | 974 个基础编程题 | Pass@1 |
| SWE-bench | 真实 GitHub Issue 修复 | 解决率 |
| LiveCodeBench | 持续更新的编程题 | 防数据污染 |

**Pass@k** 的含义：生成 k 个解，至少有一个通过测试用例的概率。

```
Pass@1: 一次生成就通过的概率（最严格）
Pass@10: 生成 10 次，至少一次通过的概率
```

**SWE-bench** 是目前最接近真实软件开发的基准——给模型一个 GitHub Issue，让它修改代码库来修复问题。

### 对话与指令遵循

| 基准 | 评估内容 | 方法 |
|------|---------|------|
| MT-Bench | 多轮对话质量 | GPT-4 打分 (1-10) |
| AlpacaEval | 指令遵循 | GPT-4 对比评判 |
| IFEval | 严格指令遵循 | 规则检查 |
| Chatbot Arena | 真实用户偏好 | ELO 排名 |

**Chatbot Arena** 是目前最受认可的评估方式：真实用户盲测两个模型的回答，投票选择更好的。基于大量投票计算 ELO 分数。

### 安全性

| 基准 | 评估内容 |
|------|---------|
| ToxiGen | 有毒内容生成倾向 |
| BBQ | 社会偏见 |
| RealToxicityPrompts | 毒性续写 |
| HarmBench | 对抗性安全测试 |

### 多模态

| 基准 | 评估内容 |
|------|---------|
| MMMU | 多学科多模态理解 |
| MMBench | 综合视觉理解 |
| MathVista | 数学视觉推理 |
| OCRBench | 文字识别 |

## LLM-as-Judge

用强大的 LLM（如 GPT-4）来评估其他模型的输出：

```
System: 你是一个公正的评估者。请对以下回答的质量打分 (1-10)。

评估维度:
1. 准确性: 信息是否正确
2. 完整性: 是否充分回答了问题
3. 清晰度: 表达是否清楚
4. 有用性: 对用户是否有帮助

问题: {question}
回答: {answer}

请给出每个维度的分数和总体评分，并说明理由。
```

### 优势与局限

| 优势 | 局限 |
|------|------|
| 成本低（vs 人工） | 存在位置偏见（倾向选第一个） |
| 可扩展 | 存在冗长偏见（倾向选更长的） |
| 可复现 | 自我偏见（倾向选自己生成的） |
| 与人类评估相关性高 | 无法评估超出自身能力的内容 |

缓解偏见的方法：
- 交换回答顺序，取平均
- 使用多个 Judge 模型
- 结合规则检查

## 评估中的常见陷阱

### 1. 数据污染（Data Contamination）

模型在训练时可能见过测试数据：

```
检测方法:
  - 检查训练数据与测试数据的重叠
  - 用模型补全测试题的选项（如果能补全说明见过）
  - 使用持续更新的基准（LiveCodeBench）
```

### 2. 过拟合基准

模型专门针对特定基准优化，但实际能力没有提升：

```
MMLU 分数很高，但实际使用中回答质量一般
→ 可能是训练数据中包含了大量类似 MMLU 格式的题目
```

### 3. 评估格式敏感

同一个问题，不同的提问格式可能导致不同的结果：

```
格式 1: "答案是 A/B/C/D 中的哪一个？" → 准确率 85%
格式 2: "请直接给出答案字母" → 准确率 78%
格式 3: "请解释你的推理过程，然后给出答案" → 准确率 88%
```

### 4. 单一指标的误导

```
模型 A: MMLU 90%, HumanEval 60%
模型 B: MMLU 85%, HumanEval 80%

哪个更好？取决于你的使用场景。
```

## 实际项目中的评估策略

### 构建评估数据集

```
1. 收集真实用户问题 (50-200 条)
2. 编写参考答案或评估标准
3. 分类: 简单/中等/困难
4. 覆盖关键场景: 正常问题、边界情况、对抗性输入
```

### 评估流水线

```
模型输出 → 自动评估 (规则 + LLM Judge) → 人工抽检 → 汇总报告

自动评估:
  - 格式检查: 输出是否符合要求的格式
  - 事实检查: 关键事实是否正确
  - 安全检查: 是否包含有害内容
  - LLM 打分: 整体质量评分

人工抽检:
  - 随机抽取 10-20% 样本
  - 检查自动评估的准确性
  - 发现自动评估遗漏的问题
```

### A/B 测试

在生产环境中比较两个模型：

```
用户请求 → 随机分配到模型 A 或模型 B
  ↓
收集指标:
  - 用户满意度 (点赞/点踩)
  - 任务完成率
  - 对话轮数 (越少越好)
  - 响应时间
```

## 小结

模型评估没有银弹。好的评估策略是多维度、多方法的组合：用基准测试了解模型的基础能力，用 LLM-as-Judge 进行大规模自动评估，用人工评估验证关键场景，用 A/B 测试在生产环境中做最终决策。最重要的是——评估要贴近你的实际使用场景。
